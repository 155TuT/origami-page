# 折间 · 渲染回退、文章收录与博客接入

> 这份记录保留了双页原型的渲染实测和三种博客框架的接入实验。正式站使用 Astro，运行方法见[项目 README](../../README.md)。

同一台机器上，桌面 Firefox 用 WebGL2 把折面的主线程提交耗时从 9 ms 降到 1 ms，Windows WebKit 窄屏用 Canvas 2D 时帧间隔更短。原型因此保留两种后端，在真实换页中选用。两篇文章都写在 HTML 中，正式发布时各自需要一个可以直接访问的地址。

[自动模式](http://127.0.0.1:4173/prototype/) · [固定 Canvas 2D](http://127.0.0.1:4173/prototype/?renderer=2d) · [固定 WebGL2](http://127.0.0.1:4173/prototype/?renderer=webgl2) · [原始测试记录](renderer-audit.json)

## 1. 浏览器如何选择绘制方式

初次访问直接显示原生文章、插图和导航。自动模式的首轮切换使用 Canvas 2D，只在真正抬起的纸面上收集帧间隔与提交耗时。读者只看文章时不会为折叠创建 WebGL 上下文。右下角「动效读数」可以查看本轮实际后端、选用理由、整次换页及折面阶段的读数。

| 时机 | 实际行为 |
| --- | --- |
| 首次完整的 2D 切换结束 | 留下折面阶段的 P95 基线。页面可见且空闲时按需加载 `fold-renderer.js`，尝试创建 WebGL2。请求 `failIfMajorPerformanceCaveat`，使用浏览器默认电源策略。设备是否采用 GPU 由真实转场决定。 |
| 用户在 GPU 还未准备好时点击 | 本轮继续使用 2D，不等待下载或编译。支持时用 `KHR_parallel_shader_compile` 查询编译完成状态，模块就绪后的下一次可比切换才试用 GPU。 |
| WebGL2 的对照轮完成 | 比较相同纸张组合、纸页尺寸、设备像素比与播放速度的折面样本。P95 帧间隔的允许回退幅度取 1.5 ms 与基线 12% 的较大值。在此范围内，如果提交至少节省 0.3 ms 且节省 20%，或帧间隔本身改善至少 1.5 ms 且改善 12%，就采用 WebGL2。否则释放试用资源，后续走 2D。 |
| 结果失去可比性 | 中途改选、调整窗口、改变播放速度的轮次不参加决策。少于 12 个连续折面帧间隔不作比较。布局签名改变后重新建立基线。已选 GPU 的连续两次有效测量明显慢于原基线，也会回退。 |
| GPU 失败 | 模块取不到、没有可用上下文、着色器失败、纹理上传失败或上下文丢失时，改用独立的 2D 画布，沿当前折叠时钟继续。一次失败在本次载入内生效，避免每帧重试。 |
| 2D 资源也不可用 | 纸张与导航原画也依赖 2D。这时直接使用原生文章和文字链接。用户开启「减少动态效果」时直接切页。以该偏好初次载入不会探测 GPU。 |

WebGL2 与 2D 共用同一组姿态、纸面 UV、材质色、缩放和平均深度排序。GPU 每个折面帧上传 64 个投影顶点和 336 个三角索引，约 1.4 KiB，一次 `drawElements` 画整张纸。横线纸和方格纸的纹理在首次使用时上传，之后按页复用。释放某页的纸纹缓存时也释放对应的 GPU 纹理。正反面、折面明暗和线距衰减在着色器里计算。平均深度排序保持原视觉，交错纸层仍有原模型的遮挡限制。平纸、正文、静态导航和最后的平移仍走原来的路径。[共享几何](../../src/lib/fold/paper.js) · [GPU 绘制代码](../../src/lib/fold/fold-renderer.js) · [选择与回退](../journal.js)

同一个 Canvas 一旦取得一种上下文就不能再改取另一种类型，所以两层各用自己的元素。只显示正在工作的那层，到站后收回大绘图缓冲。常规播放无需 GPU 同步读回、`gl.finish()` 或硬件跑分。显卡身份和 GPU 计时仅在本地实验里读取。[Canvas 上下文规则](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/getContext) · [WebGL 实践建议](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) · [并行着色器编译扩展](https://registry.khronos.org/webgl/extensions/KHR_parallel_shader_compile/)

## 2. 本机实测

### 相同动画，两种绘制方式

**怎样读浏览器名称。** Safari 是读者在 iPhone、iPad 或 Mac 上打开的浏览器，WebKit 是 Safari 用来排版、绘制网页的开源引擎。下面的 Windows WebKit 一行使用 Playwright 的引擎测试构建，用来发现浏览器实现之间的差异。iPhone 和 Mac 上的 Safari 仍需分别实测，不应根据这行数字给所有 Safari 用户指定 2D。[WebKit 项目说明](https://webkit.org/) · [Playwright 与正式版 Safari 的区别](https://playwright.dev/docs/browsers#webkit)

2026-11-04，在一台 Windows 笔记本上用本机 HTTP 串行运行五种条件。处理器是 AMD Ryzen AI 7 H 350，本机正式版 Chrome 156.0.8078.80 与 Edge 156.0.4314.58 的 WebGL 上下文都报告 **NVIDIA GeForce RTX 5060 Laptop GPU，ANGLE / D3D11**。Chrome 同时报告 Canvas 2D、光栅化与 GPU 合成都已启用。因此这次比较的是逐面裁剪、贴图的 2D 路径和一次网格绘制的 WebGL2 路径。Firefox 和 WebKit 的驱动标识可能会被泛化，表中仅以实际浏览器与视口区分。

每种条件依次用 **2D → WebGL2 → WebGL2 → 2D** 开四个新浏览器进程，每个进程完成四次换页。共 80 次，每个单元格含八次测量。同一进程内用同两篇文章、相同纸纹、1× 速度和原生 `requestAnimationFrame`。指定 GPU 的进程等它就绪后才测切换，启动成本另列。表格取八次**单次换页 P95 的中位数**，单位都是毫秒。「提交」只计抬起的纸面上 JavaScript 投影、排序和提交绘制的同步时间。「整段间隔」还包括文章淡出与鹤形归位。[逐次测量、区间和样本数](renderer-audit.json)

| 环境 | 折面提交，2D → WebGL2 | 折面回调间隔，2D → WebGL2 | 整段回调间隔，2D → WebGL2 |
| --- | ---: | ---: | ---: |
| Chrome 156，1366 × 850，DPR 1 | **1.1 → 0.3** | 10.2 → 10.15 | 10.2 → 10.1 |
| Microsoft Edge 156，1366 × 850，DPR 1 | **0.95 → 0.3** | 10.1 → 10.1 | 10.1 → 10.15 |
| Chrome 156，390 × 844，DPR 3，CPU 模拟降速 4 倍 | **4.0 → 1.2** | 10.1 → 10.1 | 10.1 → 10.1 |
| Playwright Firefox 156，1366 × 850，DPR 1 | **9.0 → 1.0** | 12.12 → 12.12 | 12.1 → 12.1 |
| Windows 上的 Playwright WebKit 26.6，390 × 844，DPR 3 | 1.0 → 1.0 | **28.5 → 34.0** | **34.5 → 39.0** |

Chrome 桌面 2D 的折面提交 P95 范围为 0.9–1.1 ms，WebGL2 为 0.3–0.4 ms。Firefox 每个折面帧省下的主线程时间尤其多，页面的排版、输入、插件代码可以使用这部分余量。Chrome、Edge 和 Firefox 在本实验里的回调节奏都相当稳定，本次没有测出物理显示帧率提高。WebKit 窄屏的 2D 与 GPU 提交都落在 1 ms 的计时档，换用 GPU 却拉长了帧间隔。按显卡型号或单独一次绘图耗时选后端会漏掉这种情况。

**自动选择另跑了三轮真实切换。** Chrome 与 Firefox 的顺序都是「2D 基线 → GPU 对照 → 继续用 GPU」。WebKit 窄屏依次是「2D 27 ms → GPU 33 ms → 回到 2D 29 ms」，这里的数字为各轮折面帧间隔 P95。三个浏览器只读首页时对 GPU 模块均为零请求，三次切换后分别只请求过一次。再给 Chrome 的 GPU 提交人为加 4 ms，下一次切换也回到了 2D。六入口共用同一纸鹤的测试另走了五次换页和一组连续改选，最多保留两张大纸纹。

### 启动、GPU 时间与画质

- **初始化确实有成本。** 指定 GPU 的两次全新桌面 Chrome 进程中，模块抵达用时 4.0–4.5 ms，随后建立资源与等待程序就绪共 139.1–179.2 ms，其中同步 `getContext` 占 102.9–142.2 ms。自动模式的一次独立测试中，这三个数分别为 4.6、52.5、8.8 ms。Windows WebKit 自动试用的同步建上下文甚至达到 293 ms。浏览器和驱动热度会影响这些数。空闲调度避开了首屏与正在播放的折叠，已经进入的同步驱动调用仍可能推迟同时到来的输入。固定 2D 与初始「减少动态效果」模式都实测为零 GPU 模块请求。当前按需加载的 GPU 文件是 6,717 字节，未压缩。
- **GPU 本身另计。** 在桌面 Chrome，另用 `EXT_disjoint_timer_query_webgl2` 每八次 `drawElements` 异步抽测一次，四轮得到 78 个有效样本。GPU 绘制用时中位数为 0.0075 ms，P95 为 0.0772 ms，最大 0.6080 ms。查询只包围绘制调用，未覆盖顶点和纹理上传、浏览器合成或屏幕扫描。Canvas 2D 没有对应的公开逐次 GPU 计时接口，不能用这个数直接算两个后端的 GPU 加速倍数。[Khronos 计时查询规范](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/)
- **内存按需要分配。** 每张 765 × 500 的桌面纸纹上传一份 RGBA8 纹理约为 1.46 MiB，两张约 2.92 MiB，叠加在静态 2D 纸纹之上。运动层绘图缓冲、驱动副本与抗锯齿还有额外开销。切换结束两个过渡 Canvas 都回到 1 × 1，自动判定保留 2D 时删除 GPU 程序、缓冲与纹理。没有测显卡总分配量或整机功耗。
- **五个固定姿态做了画面对照。** 相同时间点两条路径得到相同折叠进度和缩放。缩到 0.5014× 时两者都折到 71.7%。在起折的横线纸和正在打开的方格纸上，同一姿态只去掉 GPU 纸纹，纸面内至少一个 RGB 通道变化 ≥3 级的像素分别占 10.94% 和 23.61%。这证明两种花纹都实际画到了折面。两后端对应纸面重叠区域的 RGB 平均绝对差约 0.39、0.61 级（每通道满量程 255）。接近成鹤时，可见的边缘差异更大，0.35× 那一帧为 4.26 级。2D 有补接缝的细描边，GPU 依赖多重采样，两者的翼尖并非逐像素一致。
- **故障验证。** 用 `WEBGL_lose_context` 在纸已抬起时丢失上下文，当前纸改走 2D 并抵达目标，随后还可以返回。分别拦掉 GPU 模块、上下文创建、着色器链接、纹理上传，文章均可抵达。禁用 2D、仅阻止导航图标的 2D，或在播放中派发 2D 上下文丢失事件，均保留了文字换页。还检查了无服务器的 `file://`、键盘、改选和导航点击命中。[上下文丢失事件](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextlost_event)

四倍 CPU 限速仍在同一台 Windows 机器、同一块笔记本 GPU 上运行。Windows WebKit 也不能代表某款 iPhone。对 Android/iOS 真机、60/120 Hz 实际上屏与电池续航，还需要相应设备的呈现帧记录和功耗数据。[Chrome 设备模拟的范围](https://developer.chrome.com/docs/devtools/device-mode) · [Playwright 的浏览器构建说明](https://playwright.dev/docs/browsers)

**复跑。** 在项目目录启动 `python -m http.server 4173 --bind 127.0.0.1`。在装有 Playwright 的 Node 测试环境中运行以下命令。右下角「动效读数」适合在自己的手机上检查实际走了哪条路径。[采样脚本](../../scripts/bench.cjs)

## 3. 目前的文章能被搜索引擎抓到吗

**原型的初始响应里有两篇文章，共用一个文档地址。** 两篇各有 `<main>` 下的 `<article>`、`<h1>`、`<p>` 和带文字的 `<a href>`。Canvas 只承载插画、纸纹、图标和转场，正文在折叠前后都保留在 HTML 中。搜索引擎可以直接从源码中提取文字。

| 检查 | 当前 demo 的实际结果 |
| --- | --- |
| 初始 HTTP 响应 | `GET /` 返回 200，原始 HTML 中有两篇 article、两个标题和两段中文正文，只有一个文档标题和一条通用描述，未设置 canonical。 |
| 禁用 JavaScript 后点击「散步笔记」 | URL 变为 `/#river`，浏览器只发出最初那一次文档请求。第二篇在源码里，仍为 `visibility:hidden` 且带 `inert`，屏幕继续显示第一篇。`#river` 也不对应实际元素 ID `article-river`。 |
| 启用 JavaScript | 控制器识别 hash，切换可见文章、整页标题和导航状态。独立请求测试用的 `/posts/river/` 在当前 demo 返回 404。 |

Google 对 JavaScript 网站建议用带真实 `href` 的链接和可独立请求的路径来区分页面，避免用片段承担不同内容的路由职责。它可以渲染 JavaScript，但不会为收集文章而模拟读者点击所有按钮。无脚本测验检验的是内容能否直接取得，实际收录、展现标题与排名要在公开部署后才能观察。[Google 的 JavaScript SEO 指南](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) · [可抓取链接](https://developers.google.com/search/docs/crawling-indexing/links-crawlable) · [URL 结构建议](https://developers.google.com/search/docs/crawling-indexing/url-structure)

**正式发布的最小改动**是让每篇文章有一个永久地址。例如请求 `/posts/river/` 直接返回河岸文章的完整 HTML、对应的标题、描述和指向该页的绝对 canonical。导航和上下篇链接都指向这个路径。已有博客应沿用已有 permalink，原有目录页、RSS 和站点地图也引用同一地址。不存在的文章返回 404。有信息价值的插图提供可读图注或替代文字，装饰纸纹继续对读屏隐藏。上线后可用 Search Console 的网址检查核对获取的 HTML、渲染结果及 Google 选择的规范页。[Google 的规范网址说明](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

## 4. 换页时，谁来处理点击

Canvas 临时绘制折纸。链接接收点击、触摸和键盘操作，控制器判断何时复用缓存。现有两张动效 Canvas 与归位小图都设了 `pointer-events:none` 和 `aria-hidden="true"`。实测折面出现在屏幕上时，导航位置的命中元素仍属于原来的链接，正在播放也能改选目标。再覆盖一层接收点击的透明元素，会额外接管文字选择、链接菜单、滚动和键盘焦点。

移植到多篇文章时，可以按照下面的顺序增强导航。

1. 初始 HTML 先给出普通文章链接。只增强站内、同源、未被处理、无修饰键的主键点击或键盘激活。Ctrl/Cmd/Shift/Alt 点击、中键、下载、其他浏览目标与同页目录锚点交给浏览器。
2. 链接获得焦点或指针停留时，可按需预取目标文档。文章请求缓存按规范 URL 与内容版本组织，纸纹与 GPU 资源按布局、文章和模型组织。这是两种不同的缓存。目前 demo 的两篇都在同一 HTML 中，所以只实现了纸纹、插图与 GPU 资源复用。
3. 普通换页保留当前正文，收到成功的目标文档后再开始折叠，或并行准备，但必须在新纸展开前有目标内容。连续点 A、B、C 时只保留最后一次意图。可取消前一次请求，晚到的结果也须核对导航序号。网络、解析或动效失败时直接打开目标原始链接。
4. 旧鹤归位时交接文章，新页展平后恢复交互，更新标题、描述、canonical、导航状态和读屏提示，并按进入方式管理标题焦点。已有路由器时由它统一更新历史。自行增强时一次成功导航只写一次历史，处理 `popstate` 时恢复现有条目、滚动和页内锚点。

## 5. Hexo、Hugo 和 React + TypeScript + Vite

在独立临时目录为三条路线各生成两篇样例，部署在本机静态服务器的 `/blog/` 子路径。三者都用普通链接从第一篇进入第二篇。下表记录三组样例的生成结果和浏览器表现。[测试输出](renderer-audit.json)

| 实际生成配置 | 禁用 JS 后深链接与导航 | 还验证了什么 |
| --- | --- | --- |
| Hexo 8.1.2，Markdown 文章 + EJS 主题 | 两个页面分别生成 HTML，第二页有自己的 h1 和正文 | 链接保留 `/blog/` 前缀，canonical 指向对应文章，缺失路径 404 |
| Hugo 0.169.0，Markdown + Go 模板 | 两篇可通过各自的永久地址直接阅读和切换 | `.RelPermalink` 保留子路径，`.Permalink` 生成该页的绝对 canonical，缺失路径 404 |
| React / React DOM 19.3.0、TypeScript 6.0.3、Vite 8.3.3 | 普通 CSR 构建的原始根节点为空。构建时为两条路由预渲染后，两份 HTML 都有正文 | 样例通过 TypeScript 检查。预渲染的第二页可从深链接加载，`hydrateRoot` 后按钮可交互，浏览器未报 hydration 错误 |

### Hexo

把稳定的导航壳和动效 Canvas 放到主题的公共 layout 或 partial，把文章保留在 post 模板的 `<article>` 中。EJS 的 `<%- page.content %>` 输出 Hexo 已渲染的正文，导航用 `url_for(post.path)`，canonical 可取文章 permalink。按正常生成流程就能覆盖分享、刷新、禁用 JS 和爬虫访问。当前 demo 启动时一次查询全部文章，迁移时要改成“现有文章 + 本次要打开的文章”，并在内容替换后重新取得标题、插图与导航锚点。[Hexo 模板](https://hexo.io/docs/templates) · [链接与根路径 helpers](https://hexo.io/docs/helpers)

如果接进这台机器上已有的 Hexo 博客，还有一项实际约束。其配置为 Hexo 8.1.2、Redefine 2.9.0，保留日期型 permalink，并开启了 `global.single_page: true`。主题初始化的 Swup 已经负责 `#swup` 内容替换、预取与滚动，也带自有的滑动转场。可以把折纸接到同一个 Swup 实例的出场与入场等待钩子，让它在合适时刻替换正文，给相同容器只留一个可见转场。持久画布放在被替换容器外，新文章就绪后重新测量。在此方案下，折纸自身无需再发文章请求或另外 push 一条历史。此次检查了主题配置和生命周期代码，主题改造未在已有博客中执行。[Swup 各阶段与可等待的 hooks](https://swup.js.org/hooks/)

### Hugo

把导航和动效宿主放在共享 `baseof.html`，在单页模板中输出 `<article><h1>{{ .Title }}</h1>{{ .Content }}</article>`。栏目或文章循环中用各页的 `.RelPermalink` 构建链接。实测版本使用 `layouts/page.html`，已有主题应遵循其版本和模板查找顺序。静态文件与 Hugo Pipes 的指纹资源均可使用，控制器需要拿到实际发布的脚本和模型地址。当前 GPU 模块默认从 `journal.js` 的同级目录按文件名加载。若给 GPU 文件单独加指纹，要从模板把生成地址传给加载器，或保留这个文件的稳定名称。[Hugo 模板结构](https://gohugo.io/templates/types/) · [正文输出](https://gohugo.io/methods/page/content/) · [相对永久链接](https://gohugo.io/methods/page/relpermalink/)

Hugo 直接导航时会载入新文档。允许原生导航就已经能阅读。若要让一只鹤在同一条时间轨上完成旧页收回、新页展开，需要一个持久的客户端壳，拦截合适的真实链接，获取下一份静态 HTML 并替换文章。对于任意文章长度，继续折可见纸窗，另外保存正文滚动位置，避免把长文高度变成大纹理的像素预算。

### React + TypeScript + Vite

- **选择文章的初始输出。** 单纯用 `createRoot` 渲染的静态入口可以在支持 JS 的浏览器阅读，但普通 HTTP 抓取和许多分享预览先看到空壳。文章集合在构建时已知时，遍历 slug，用同一 React 组件产出每篇 HTML，客户端再调用 `hydrateRoot`。经常在请求时变化的内容也可选 SSR。Vite 提供构建能力，按文章生成页面需要额外的构建步骤或相应框架。[Vite 的预渲染与 SSG](https://vite.dev/guide/ssr.html#pre-rendering-ssg) · [React hydration 约束](https://react.dev/reference/react-dom/client/hydrateRoot)
- **确定 DOM 的所有者。** 路由、正文、标题、焦点和选中状态由 React 管理。把一个持久的 `<canvas ref>` 交给折纸运行时，用 ref 保存时钟、缓冲区和动画 ID。逐帧顶点和透明度无需进入 React state。若路由变化就卸载旧文章，折到一半会失去纸面和锚点，应该由共同的 layout 保留旧页直至交接。
- **处理初始化与卸载。** 当前脚本在加载时查 `document`、DOM 节点和媒体查询，直接引入服务端渲染路径会出错。移植时把几何和数据做成无 DOM 的模块，把浏览器部分封装成显式的挂载与清理。清理 rAF、计时器、观察器、事件监听、纹理和程序。开发模式下 StrictMode 会额外演练 Effect 的挂载与清理。HMR 后也要避免第二个控制器抢同一只鹤。[React StrictMode](https://react.dev/reference/react/StrictMode)
- **确定路由、子路径与静态托管规则。** `/blog/posts/river/` 在重新加载时也应返回目标文章。SSG 发布对应目录的 `index.html`。纯 SPA 使用 history 路由还依赖托管端回写入口，全部未知路径回写 200 容易产生软 404。Vite 的 `base`、路由前缀、模型和 GPU 模块路径要一起验证。优先使用构建器生成的资源 URL 或明确的公共路径，避免把 demo 的经典脚本全局变量直接拼进 ESM。[Vite 静态部署](https://vite.dev/guide/static-deploy.html)
- **保持服务器输出与客户端第一帧一致。** 服务器先输出可读文章。屏宽、DPR、GPU 能力与用户的减少动态偏好交给客户端挂载后读取，不用这些浏览器值改变首次 hydration 的正文结构。Vite 负责 TypeScript 转译，发布前另跑 `tsc --noEmit`。类型上可分别描述 2D、WebGL2 与文字模式，让上下文丢失时的生命周期清楚可查。[Vite 的 TypeScript 处理](https://vite.dev/guide/features.html#typescript)

对于已有 Hexo 博客，可以先接一对真实 permalink，把浏览器后退、深链接与中途改选跑通，再加其余导航图标。对于新建的 React 博客，先在禁用 JavaScript 的浏览器里读通两篇预渲染文章，再接同一套折面播放器。这两个验证都可以在上线前完成。
